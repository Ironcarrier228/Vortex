# Архитектура VORTEX

## 1. Почему Tauri + three.js (а не WinUI 3 / C++ + DirectX)

Заданный стек оставлен без изменений, и вот почему это осознанный выбор, а не компромисс:

| Критерий | Tauri + WebGL | WinUI 3 + DirectX 12 | Примечание |
| --- | --- | --- | --- |
| Скорость разработки «эффектного» визуала | очень высокая: шейдеры, bloom, перехода — десятки строк | высокая, но вручную: pipeline states, descriptors, root signatures | Основная цель проекта — визуал, а не изучение D3D |
| Пост-обработка из коробки | `EffectComposer` + `UnrealBloomPass` + собственный `GradePass` | нужно самому писать bloom-цепочку (≥600 строк) | |
| 3D-физика графа | `d3-force-3d` — одна зависимость | портировать/писать force-directed в C++ | |
| Итерация по графике | hot reload (Vite), правка шейдера — мгновенно | пересборка C++ | |
| Доступ к Windows API | полный (Rust: WASAPI, iphlpapi, ETW, NTFS USN) | полный | Данные всё равно собираются нативным кодом |
| Размер дистрибутива | ~8–12 МБ (WebView2 есть в Win10/11) | ~5–8 МБ | Оба малы |
| Накладные расходы рендера | WebGL2 поверх ANGLE/D3D11 — на 1080p-графике «визуализации» разницы с D3D12 нет | | 60 FPS достигаются в обоих случаях |

**Когда стоило бы сменить стек:** если бы требовались десятки миллионов частиц с compute-шейдерами, задержка захвата звука <5 мс для аудио-обработки или интеграция в shell-компоненты Windows (Jump Lists, thumbnails). Ничего из этого в задаче нет. Если позже понадобится WebGPU — heist: three.js уже поддерживает `WebGPURenderer`, и переход не потребует менять архитектуру.

## 2. Слои

```
┌─────────────────────────────── src/ (TypeScript, three.js) ───────────────────────────────┐
│  scenes/audio   scenes/network   scenes/disk      ← независимые модули сцен (SceneModule)   │
│         │              │               │                                                    │
│         └──────────────┴───────┬───────┘                                                    │
│                        core/scene.ts  (интерфейс SceneModule + SceneContext)               │
│                                │                                                            │
│  core/gesture/         — рука как указатель: HandSource → GestureController → PointerHub    │
│  core/render/engine.ts — один WebGL-контекст, Render → Bloom → Grade → Output, переходы    │
│  core/hud/hud.ts       — вкладки, панели, настройки, тултипы, подтверждения                 │
│  core/audio/bus.ts     — спектр из WASAPI или микрофона → нормализованные значения 0..1     │
│  core/transport.ts     — invoke/listen (Tauri) + мок-бэкенд для браузера                    │
│  core/prefs.ts         — настройки (localStorage, реактивные подписки)                      │
└───────────────────────────────┬────────────────────────────────────────────────────────────┘
                                │ invoke (запрос) / events (потоки)
┌───────────────────────────────┴───────── src-tauri/ (Rust) ─────────────────────────────────┐
│  commands/*  — тонкий слой: валидация аргументов, запуск потоков, отправка событий          │
│  providers/audio     — WASAPI loopback → vortex-core::audio::Analyser → события 60 Гц        │
│  providers/network   — GetExtendedTcpTable/UdpTable (PID ↔ сокет) + diff снимков             │
│  providers/disk      — jwalk-обход (позже: MFT/FSCTL_ENUM_USN_DATA), дерево, корзина          │
│  providers/winapi.rs — is_elevated(), process_path(), RAM (прямой FFI, без крейта windows)   │
│  providers/recycle.rs— SHFileOperationW + FOF_ALLOWUNDO (удаление только в корзину)          │
└───────────────────────────────┬─────────────────────────────────────────────────────────────┘
                                │
                    crates/vortex-core (чистый Rust, тесты на любой ОС)
                    audio.rs  — FFT/полосы/сглаживание     netdiff.rs — что появилось/исчезло
                    disk.rs   — сборка дерева, категории файлов
```

Ключевое правило: **провайдеры не знают о Tauri, команды не знают о графике, сцены не знают о Rust.**
Экран можно заменить (например, dotnet-хост вместо Tauri) или мок-бэкенд на синтетике — код сцен не меняется.

## 3. Потоки данных

| Поток | Источник | Транспорт | Частота |
| --- | --- | --- | --- |
| Спектр звука | WASAPI loopback (Rust) | событие `vortex://audio/frame` (64 полосы, дБ) | ~60 Гц |
| Статус аудио | — | `vortex://audio/info` | по изменению |
| Соединения | IP Helper (Rust) | `vortex://net/snapshot` (список + `added`/`removed`) | 0.5–1 Гц (настройка) |
| Скан диска | jwalk (Rust) | `vortex://disk/stats` (инкрементально) | ~4 Гц во время скана |
| Содержимое каталога | дерево в Rust | `invoke disk_children` | по клику |
| Система | — | `vortex://sys/info` + `invoke sys_info` | при старте |
| Смена сцены | UI | `vortex://scene/change` (всем окнам) | по действию |
| Кадры кисти | веб-камера → MediaPipe WASM (в процессе UI) | прямой вызов `push(frame)` | 30 Гц (распознавание) |
| Курсор/жесты | `GestureController` | `update(dt)` → `PointerHub` + сцены | 60 Гц (кадр рендера) |

Данные аудио сознательно идут событием, а не через SharedArrayBuffer: 64 float на кадр ≈ 256 байт,
сериализация дешевле синхронизации потоков, а задержка в один кадр для визуализации незаметна.

## 4. Рендер-пайплайн

```
сцена (THREE.Scene)
   └─ RenderPass            → HDR-таргет (HalfFloat, MSAA 4x)
        └─ UnrealBloomPass  → сила/радиус/порог модулируются энергией звука
             └─ GradePass   → ACES, контраст/насыщенность, хром. аберрации,
                              виньетка, зерно + СМЕШИВАНИЕ С ПРЕДЫДУЩЕЙ СЦЕНОЙ
                              (uPrev, uMix), радиальный варп и вспышка перехода
                  └─ OutputPass → sRGB на экран
```

**Переход между сценами** (`Engine.#renderFrame`): уходящая сцена рендерится в отдельный HDR-таргет
`#prevTarget`, приходящая идёт обычным путём, а `GradePass` смешивает их по `uMix` и добавляет
радиальный варп (`uWarp`) и вспышку (`uFlash`). Получается «камера летит сквозь пространство»,
а не кроссфейд. Прогресс 0→1 за 1.15 с; сцены получают его через `SceneState.enter` и сами
разводят/сближают камеры и объекты.

## 5. Производительность и энергопотребление

| Механика | Где | Что даёт |
| --- | --- | --- |
| Кадры «по требованию» | `Engine.#schedule` | на паузе (Space) рендера нет вовсе: цикл заменяется на `setTimeout(200)` |
| Полная остановка сцен на паузе | `Engine.#updateScenes` | физика графа, анимации и звук не считаются |
| `document.hidden` → idle | `#isIdle()` | свёрнутое окно не жжёт CPU |
| Адаптивное разрешение | `#adaptQuality` | масштаб рендера 1.5 → 0.62 по времени «полезной» работы кадра (>19 мс вниз, <12.5 мс вверх) |
| Лимит FPS | `fpsCap` | 30/60/без лимита, пропуск vsync |
| WASAPI-пауза | `audio_set_active(false)` | поток продолжает осушать буфер, но FFT не считается (0 % CPU на анализ) |
| GPU-анимация частиц | `PARTICLES_VERTEX` | 120 000 частиц без работы на CPU в кадре |
| `simulation.alpha() < 0.005` | `ForceGraph.update` | физика графа засыпает, когда всё устоялось |
| Кэш процессов/PID | `ProcCache` (TTL 30 с) | `QueryFullProcessImageName` не вызывается лишний раз |

Целевой бюджет: работа кадра ≤ 12 мс; HUD-статистика обновляется 4 раза в секунду, спарклайн — 10 раз.

## 6. Мультиоконность

`open_output_window` создаёт окно с меткой `output`: без декораций, `always_on_top`, fullscreen на
втором мониторе (если он есть). Окно вывода — тот же бандл: `main.ts` определяет режим через
`getCurrentWindow().label`, поэтому HUD не создаётся, а сканирование диска не инициируется
(`SceneContext.mode === 'output'`). Синхронизация сцен идёт событием `vortex://scene/change`,
данные — теми же событиями от бэкенда (они вещаются во все окна).

## 7. Безопасность

* **Только корзина.** `SHFileOperationW` с `FOF_ALLOWUNDO`: файл можно восстановить штатными средствами Windows.
* **Три барьера перед удалением:** путь абсолютный и существует; путь внутри ранее просканированного
  корня и не равен ему; UI обязан получить подтверждение (`Hud.confirm`) — иначе команда не вызывается.
* Сканирование никогда не удаляет и не изменяет данные; симлинки не раскрываются (`follow_links(false)`),
  чтобы не выйти за пределы корня.
* Сеть: только чтение таблиц соединений. Никаких пакетов не перехватывается, ETW-провайдер (этап 3)
  читает счётчики ядра в режиме мониторинга.
* Звук: захват системного вывода (loopback) — данные не покидают машину и не пишутся на диск.

## 8. Права администратора

Приложение полностью работает без admin:

| Функция | Без админа | С админом |
| --- | --- | --- |
| Список соединений PID ↔ IP/порт | ✅ IP Helper | ✅ |
| Объём трафика по процессам | ❌ | ✅ ETW `Microsoft-Windows-Kernel-Network` (этап 3) |
| Скан диска | ✅ jwalk (минуты на HDD) | ✅ + MFT/USN (секунды) |
| Захват системного звука | ✅ WASAPI shared loopback | ✅ |
| Удаление в корзину | ✅ | ✅ |

Определение прав — `is_elevated()` через токен процесса (не по членству в группе, чтобы на админской
учётке при обычном запуске правда была правдой). Флаги доступных функций уезжают в HUD чипами
`АДМИН` / `БЕЗ АДМИНА`.

## 9. Ужесточение CSP для релиза

В `tauri.conf.json` сейчас `"csp": null` — удобно для dev. Перед релизом поставить:

```json
"security": {
  "csp": "default-src 'self'; img-src 'self' data: blob:; style-src 'self' 'unsafe-inline'; script-src 'self'; connect-src 'self' ipc: http://ipc.localhost"
}
```

С жестами всё сходится на локальной копии: `public/mediapipe/vision_bundle.js` — свой скрипт
(`script-src 'self'`), WASM берётся из `/mediapipe/wasm` (`connect-src 'self'`). Если хочется
оставить запасной вариант с CDN, добавьте `https://cdn.jsdelivr.net` в `script-src` — иначе
без локальной копии распознавание рук будет недоступно, а остальное приложение продолжит работать.

(Шейдеры задаются строками в бандле — это не требует `unsafe-eval`; `'unsafe-inline'` нужен только для
инлайновых стилей HUD, их можно вынести в CSS-файл и убрать.)

## 10. Управление жестами (рука = указатель)

Камера — не отдельный «режим», а второй источник того же указателя, поэтому сцены не знают, чем
управляет пользователь:

```
HandSource (CameraHandSource | DemoHandSource)   ← кадры кисти 30 Гц, 21 точка
      │ push(frame)
GestureController                                ← геометрия, гистерезис щипка, позы, свайпы, удержания
      │ update(dt) каждый кадр
      ├──► PointerHub  → сцены (наведение, выбор, перетаскивание узла)   — как от мыши
      ├──► GestureOverlay → скелет, курсор, кольцо щипка, линия «рука↔объект»
      └──► события: «класс» (действие сцены); свайп/пауза/кулак — выключены по умолчанию
```

Почему так:

* **Разделение частот.** Распознавание идёт 30 Гц, а сглаживание/гистерезис/таймеры — каждый кадр
  рендера. Курсор остаётся плавным даже при «тяжёлых» кадрах модели.
* **Один указатель.** Мышь и рука обновляют один и тот же `PointerHub`, поэтому перетаскивание узла
  работает одинаково двумя способами, а сцены пишутся один раз.
* **Щипок = «вырвать и посмотреть».** Пока узел в руке, он растёт (у процессов до x2, у хостов до x3.6)
  и вокруг появляется вращающийся каркас — поворот кисти вращает узел, панель сцены показывает его
  запросы. На отпускании узел остаётся закреплённым там, где его оставили (d3-force `fx/fy/fz`),
  а кнопка «Вернуть узлы» снимает все закрепления.
* **Чёрная дыра (`blackHole.ts`).** «Мусорка» сцены: выкинутый орб вырывается из цепочки окончательно.
  Собрана без шейдеров и текстур (весь слой проверяется в Node, где нет ни `document`, ни WebGL):
  чёрная сфера горизонта событий, фотонное кольцо и широкий ореол из `RingGeometry` с вершинными
  цветами (в аддитивном смешивании чёрный невидим — градиент «гаснущее наружу» получается сам),
  три наклонных слоя аккреционного диска из `Points` с разной скоростью вращения и искры на вспышке.
  Кольца разворачиваются к камере (`faceCamera`), иначе плоский диск виден с ребра.
* **Бросок = поглощение.** `ForceGraph.throwNode(node, velocity)` переводит узел в режим «снаряда»:
  скорость каждый кадр доворачивается в сторону дыры (`THROW_TURN`), поэтому затягивание идёт по спирали
  и не может промахнуться; если узел не долетает за `THROW_PATIENCE`, дыра тянет сильнее. У горизонта
  событий связи рвутся (`#severLink`), узел за `DEVOUR_TIME` схлопывается в точку, исчезает из графа и
  запоминается в `#swallowed` — новые снимки сети его не возвращают. Сама машина (узел `local`) не
  бросается: её потеря означает пропажу всей сцены.
* **Разрыв связи.** Рвать можно двумя путями: узел выкинули (бросок) или продержали вырванным дольше
  `LINK_ABSORB_START + LINK_ABSORB_TIME` — линия всосалась в орб. В обоих случаях `#severLink` ставит
  точку обрыва (`cut`), и за `CUT_TIME` оторванный конец с белой вспышкой отлетает к дальнему узлу
  (`cutT`, `cutFrom`), после чего линия исчезает из `links`. Идентификаторы разорванных связей живут
  в `#severed`, поэтому `sync()` их больше не создаёт — в отличие от живого трафика, который меняется
  сам, это ручное решение пользователя. Снимает его только «Вернуть узлы» (`unpinAll`).
* **Две руки = два орба.** `#grabbed` — массив: каждая рука держит свой узел, у каждого своя оболочка
  (`#shells`) и своя резинка. Сцена отдаёт вторую руку (`secondaryCursor` + `secondaryPinch`, порог щипка
  у неё тот же калиброванный) в отдельный путь перетаскивания, и у второй руки тоже работает бросок.
* **Щипок в пустоте.** Если щипок случился не над узлом, сцена считает, что взялись за саму сцену:
  движение руки вращает и наклоняет граф (`OrbitCamera.rotateBy`), поворот кисти доворачивает вокруг
  оси взгляда. Мышь для этого не нужна, и это не мешает перетаскиванию узлов.
* **Резинка соединений.** У выдёргиваемого узла точки крепления его рёбер не приклеены намертво:
  они вяло догоняют узел (`LINK_LAG_PULL`), поэтому линия видимо тянется; через 1.5 с линия начинает
  затягиваться в орб и за 0.8 с схлопывается и гаснет. После отпускания absorb плавно спадает —
  линии выкатываются обратно к своим узлам. Так «вырвать узел из цепочки» выглядит как вырывание,
  а не как перемещение шарика.
* **Калибровка щипка.** Абсолютный порог не работал для рук вдали от камеры и при наклоне кисти:
  и щипок, и ладонь дают большие отношения. Порог считается относительно «раскрытого» значения
  этой руки (`pinchBaseline`), масштаб кисти берётся как максимум из нескольких промеров
  (перспектива укорачивает отдельные отрезки), а расстояние между пальцами считается в 3D.
  Текущее отношение и порог выводятся в плашке («щипок 0.83 → нужно < 0.62») — это и диагностика.
* **Случайные срабатывания — это баг.** Свайп ладонью (перелистывание сцен), пауза открытой ладонью и
  кулак-«сброс» по умолчанию **выключены**: рука часто висит раскрытой, и жесты срабатывали сами.
  Детекторы остались в контроллере и включаются префами; осознанным оставлен только «класс».
* **Нормировка на размер кисти.** Все пороги считаются в долях расстояния «запястье → основание
  среднего пальца»: жест одинаково работает у монитора и в двух метрах от камеры.
* **Мягкая зависимость.** Библиотека MediaPipe подключается только при включении жестов и только
  в рантайме — тегом `<script>` (сначала локальная копия `public/mediapipe/vision_bundle.js`,
  затем CDN), потому что файлы из `public/` нельзя импортировать из кода, а импорт npm-пакета
  сделал бы зависимость жёсткой. Файлы кладут скрипты: `npm run sync:mediapipe` (библиотека + WASM,
  ≈37 МБ) и `npm run fetch:models` (модель). Без пакета, без интернета или без модели приложение
  работает как обычно — жесты просто показывают понятную ошибку в статусе.
  Скрипт синхронизации не перезаписывает уже готовые файлы (сравнивает размеры) и не валит сборку,
  если файл занят другим процессом — на Windows это штатная ситуация: WebView2 или антивирус
  держат только что прочитанный WASM, а `fs.cpSync` перед записью пытается приёмник удалить.
* **Демо-источник и честная деградация.** `?hand=demo` (или тумблер «Демо-рука») включает синтетическую
  руку: жесты можно смотреть и отлаживать там, где камеры нет (превью, CI — контроллер прогоняется на
  синтетических кадрах в `npm run smoke`). Если камеру не удалось включить (нет устройства, запрет
  доступа) или модель недоступна, приложение **само** переключается на демо-руку и пишет причину на плашке
  состояния: пустого экрана и молчания не бывает.
* **Экономный режим.** При просадке FPS рендера частота распознавания снижается (30 → 20 → 12 Гц,
  `core/gesture/rate.ts`): модель и сцена делят один GPU, и 30 Гц распознавания на слабой машине
  роняют картинку. Управление по-прежнему идёт с частотой кадров — сглаживание и гистерезис
  работают на кадрах рендера.
* **Диагностика на экране.** Плашка в правом нижнем углу всегда показывает состояние распознавания
  (`жесты · 30 FPS · GPU · модель: локальный файл`), «рук: N», причину сбоя и подсказку. Пока рука
  в кадре и всё в порядке, плашка притухает, чтобы не мешать смотреть.
* **Пустой глобус не показываем.** Координаты хостов приходят только с GeoIP (этап 3), поэтому
  до него переключение в «глобус» объясняет причину и оставляет граф; панель «Соединения» пишет
  строку диагностики («в 3D: N узлов · M рёбер»), чтобы «пусто» никогда не было загадкой.
* **Модель: где брать и как проверять.** Источники по порядку: `public/models/hand_landmarker.task`
  (офлайн, `npm run fetch:models`) → Google Storage → зеркала на CDN npm. Формат проверяется по
  контейнеру ZIP **терпимо**: у официальной модели перед сигнатурой стоят два нулевых байта
  (`00 00 50 4b 03 04`), поэтому признак «файл начинается с `PK`» отвергал валидную модель — ищем
  локальный заголовок в первых 64 байтах и запись конца каталога в хвосте.
* **Приватность.** Кадро не пишется и никуда не отправляется; на паузе/свёрнутом окне камера гасится
  (`stop()` треков), индикатор в системе гаснет.

## 11. Как добавить свою сцену

1. Создать `src/scenes/<name>/<name>Scene.ts`, реализовать `SceneModule` (`id`, `title`, `scene`, `camera`,
   `update`, `resize`, `dispose`, по желанию `activate/deactivate/onKey/hudPanel`, а также
   `resetView`/`controlOrbit`/`onGesture` — чтобы сцена понимала жесты).
2. Зарегистрировать в `main.ts`: `this.#scenes.set('name', new NameScene(context))` и добавить в
   `SCENES` в `core/hud/hud.ts` (вкладка + горячая клавиша).
3. Данные брать через `invoke`/`listen`, ни в коем случае не обращаться к DOM HUD напрямую —
   только `ctx.hud`.
4. Тяжёлую работу уносить на GPU (см. `scenes/audio/shaders.ts`) либо в Rust-провайдер.
5. Указатель брать только из `ctx.pointer` (единый для мыши и руки), а не вешать свои
   `pointermove` на canvas: иначе жест-управление в сцене работать не будет.
